02 — Engineering stack review

A developer's proposed stack — is it right?

Reviewed layer by layer. Short answer: the core is solid and worth keeping — two things are worth pushing on before it's final.

Frontend Next.js (App Router) + shadcn/ui + TypeScript Keep
Standard, well-supported, fast to build in. Server actions cut boilerplate; shadcn ships accessible components you own (copy-in, not a runtime dependency) instead of a locked-in design system. Right call for a small team moving fast.
Database + Auth Supabase — Postgres, Auth, RLS for role/portal isolation Keep
Enforcing internal/customer/operator isolation at the database layer via RLS is stronger than checking roles only in application code. One caution: RLS policies get harder to reason about as they multiply — keep them simple, test them directly, and don't treat RLS as the only line of defense; validate roles in server actions too.
CRUD Direct against Supabase — client + server actions/route handlers, no separate API layer Keep, with a caveat
Right-sized for now — a hand-rolled REST/GraphQL layer in front of the database would just be a proxy nobody needed yet. The caveat: this quietly assumes only this Next.js app ever talks to the data. If a mobile app, a partner integration, or a public API shows up later, that's a real retrofit, not a config change — worth deciding now whether that's a permanent bet or a Phase-0 simplification.
Background jobs Separate Dockerized Python server, same Postgres — polling, expiry sweeps, timers Push back
Pulling long-running/scheduled work out of the request-response cycle is the right instinct — serverless functions aren't built for polling loops. But: a second language and a second deploy pipeline is a real tax on a small team already running TypeScript everywhere else. Worth asking directly: is there a concrete reason for Python here (a library only Python has, existing team depth), or is it default habit? If it's habit, a Node/TypeScript worker — or a managed queue like Supabase's pg_cron, Trigger.dev, or Inngest — gets the same separation without a second runtime to operate.
Realtime Supabase Realtime — dashboards, notifications Keep
Already on Postgres, so this rides the existing infrastructure instead of standing up a separate pub/sub or websocket service. Minimal-additional-infra is the right bias at this stage.
AI / LLM orchestration — not specified — Missing
This is the actual product. Nowhere in the stack does it say where model calls happen, how a multi-step generation (plan → fill, per the architecture above) gets queued and retried, or how streaming output reaches the UI. That decision — inside a Next.js server action for simple calls, versus a dedicated service for longer agent loops — belongs in this stack description before anything else does.

Overall call

Keep the core: Next.js/shadcn/TypeScript, Supabase for Postgres/Auth/RLS, no separate CRUD layer yet, Realtime on Supabase. Two things to resolve before it's final — confirm Python earns its place for background jobs rather than defaulting to it, and name where AI orchestration actually lives. That second one isn't a nice-to-have; for this product, it's the part of the stack that matters most.
